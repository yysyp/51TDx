# 51TDx 产品功能文档

> 版本：v4.1.0 ｜ 包名：`com.ran.app` ｜ minSdk 26 / target 34
> 技术栈：Kotlin 2.0.20 + Jetpack Compose (Material 3) + Room 2.6.1 + MVVM

---

## 一、产品定位

51TDx 是一个**自我激励工具**，不是任务管理器。

大多数待办应用的激励方式是"完成了一项"这样一句平淡的反馈，完成之后就没有然后了。51TDx 的设计目标是把所有行为接入同一个奖励经济系统，让每一次行动都能兑换到实际的东西——一杯咖啡、一集剧、一个下午的自由。

### 核心闭环

```
行动（打卡 / 完成任务 / 完成复习）
   ↓ 自动发放
获得星星 ⭐
   ↓ 攒够后消耗
抽奖 / 兑换奖励
   ↓ 拿到真实奖励
产生下一次行动的动机
```

这条链路是整个应用的骨架。**四个功能模块不是并列的工具，而是同一套经济系统的不同入口**——打卡攒的星能抽奖，完成待办也能抽奖。因此任何一个模块都不是死胡同，用户无论从哪个功能进来，都在推进同一条进度。

### 设计原则

| 原则 | 落地方式 |
|---|---|
| 奖励必须够得着 | 定价校准为约三次打卡换一次抽奖 |
| 永不制造愧疚 | 全部文案为能力肯定式，无指责、无失败状态 |
| 最小动作零摩擦 | 完成待办只需单击复选框 |
| 努力必须被看见 | 每个模块都有历史记录页 |
| 账目必须可追溯 | 星星变动采用 append-only 账本 |

## 三、功能模块详解

### 1. 首页仪表盘

打开应用首先看到渐变等级卡，而非任务列表。信息顺序是刻意的：**先回答"我在哪"，再回答"能做什么"**，让用户保持方向感而非被任务淹没。

| 元素 | 内容 |
|---|---|
| **等级卡** | Lv 等级、星星余额、连续打卡天数、水平进度条（暖色渐变） |
| **今日目标** | 按当日获星进度填充，起始即有非零进度 |
| **今日概览** | 今日星星 / 待办数 / 进行中计划数，三个圆形计数 |
| **进行中计划** | 最多显示 3 项，超出显示"还有 N 项…" |

**文案策略**：全部为能力肯定式。例如进度过半显示"进度过半了，继续保持"，而非"还有一半没完成"。基于自我决定理论，愧疚感是行为改变的最大阻力，会导致用户直接放弃应用。

---

### 2. 抽奖（🎰）

用可变比率强化（Skinner）机制驱动：奖励频率不可预测，因此行为能长期维持。

| 功能 | 说明 |
|---|---|
| **三段式仪式** | 点「开始」滚动 → 点「停」揭晓 → **刮开涂层**才看到结果 |
| **加权随机** | 每个奖项有独立权重字段，权重越高越易被抽中 |
| **星星定价** | 每个奖项单独定价（1-30 星），花费从抽中的那个奖项扣除 |
| **权重即概率** | 权重栏就是中奖率，填 10 即 10%；全体合计恒为 100% |
| **自动均化** | 改动任一权重，其余奖项按比例自动让出/分出空间，总和恒为 100% |
| **允许欠账** | 星星不够也能抽，扣成负数显示，不拦截 |
| **奖项管理** | 完整增删改，含名称、描述、emoji、权重、星星价、是否头奖 |
| **中奖记录** | 最近 50 条，头奖（三个最贵的）带高亮标签，仅为视觉标记，不影响概率 |

### 三段式仪式感

抽奖拆成"开始 → 停止 → 刮开"三拍，而不是一次揭晓：

- **开始/停止由玩家控制**。悬念来自自己按下停止的那一下，而不是一段被动等待的计时动画。因此停止后的减速只有 6 步——期待感已经由玩家的手给出了，再长的收尾只是死时间。
- **刮开是刻意加的门槛**。结果凭空出现时，等注意力落上去它早就送到了；用几秒把涂层擦掉，这几秒的介入感才是"中奖"区别于"通知"的关键。擦开达到 45% 卡片面积即自动揭晓——一个永远擦不完的奖品是 bug，不是谜题。

### 权重即概率与自动均化（v4.0.0）

**权重栏就是中奖率**。此前权重是任意数值（总和 281），填 46 既不表示 46% 也不知道会落在多少分母上。现在：

- 权重恒等于百分比，全体**合计恒为 100**
- 改动任一奖项，其余奖项按**比例**自动让出或分出空间
- 每个奖项最少 0.01%，任何人都不可能被设成抽不到

均化用**最大余数法**：先向下取整，再把余下的单位按小数部分从大到小补齐，因此总和精确等于 100.00，不会出现 99.98 或 100.03 —— 一个加起来不等于 100 的奖池，意味着界面显示的概率和实际抽奖用的概率对不上。

### 两位小数与三种触发（v4.0.1）

首版实现只改了整数百分比，而且**均化代码当时并没有真正写进文件** —— 真机测试发现"改权重毫无反应"，根因是 `savePrize` 仍是旧的一行实现（此前的脚本替换中途抛异常，覆盖掉了新代码）。教训：批量替换后必须回读确认目标函数确实存在。

**两位小数**：`PrizeEntity.weight` 由 `Int` 改为 `Double`（REAL 列）。18 个奖项挤在 100 个百分点里时，整数精度会让某个奖项无处可让——改一项要动 17 项，每项至少让出 1 个点，形状立刻塌陷。两位小数是这套均化能工作的最低精度。

**计算全在整数域完成**：`PrizeBalancer` 内部以**百分之一**为单位做整数分配（`UNITS = 10000`），最后才除回小数。用浮点缩放再逐项四舍五入会在 18 行上累积误差。

**三种触发点**都走 `RanRepository`（不是 UI 层），所以无论从哪个入口改，不变量都成立：

| 操作 | 行为 |
|---|---|
| 修改某项概率 | 该项取输入值（两位小数），其余按现有比例分摊剩余额度 |
| 新增奖项 | 新项取输入值，原有各项按比例让出空间 |
| 删除奖项 | 被删项的份额按比例回填给其余项 |

删除最容易漏：不回填的话池子会掉到 93，此后**每个留存奖项的实际概率都悄悄高于它标称的数字**，而界面上完全看不出来。

写入通过 `PrizeDao.replaceAll` 的 `@Transaction` 完成。一次均化要改 18 行，中间态总和不足 100，中途失败会留下一个"显示概率与实际概率不符"的奖池，且界面上没有任何提示。

**已验证的五个场景**：改单项、新增、删除、极小值（0.01%）、连续 50 次均化 —— 总和偏差次数为 0。

**删除头奖保底**（v4.0.0）：此前有一层"距上次头奖越久，头奖权重越高"的保底机制，以及首页的「头奖进度」进度条。现已全部移除（`JackpotEngine` 整个删除），头奖仅保留为中奖记录里的高亮标签，不再影响概率。抽奖退化为纯粹的加权轮盘：每次独立、恒定概率，无记忆性。

### 权重调优：前三项占近一半（v2.1.0）

前三项（1元 / 15分钟屏幕 / 免一次家务）合计从 **31.6% 提到 49.7%**，同时中段权重按比例压缩约 43%，使奖池总权重从 342 降到 281。

| 项 | 调整前 | 调整后 |
|---|---|---|
| 前三项合计 | 31.6% | **49.7%** |
| 头奖合计 | 2.72%（1/37 抽） | 3.33%（1/30 抽） |
| 单次期望花费 | 8.16 ⭐ | 6.80 ⭐ |
| 每 30 次抽奖的小奖次数 | 9.5 次 | **14.9 次** |
| 每 30 次抽奖的头奖次数 | 0.8 次 | **1.0 次** |

**为什么加大小奖反而"不打击积极性"**：真正劝退儿童的不是抽不到大奖，而是**反复看到空白结果**。前三项接近五成，意味着连抽两次必有一次"到手"。中段压缩是为了保住梯度——如果小奖吞掉全部概率，"随便抽抽就行"，抽奖会退化成开糖。

**代价（如实记录）**：连续抽到同一个具体小奖的概率从 2.9% 升到 7.0%。这是前三项变重的必然结果，可以通过把前三项降到 45% 左右缓解。

### 宠物价格联动下调（v2.1.0）

抽奖期望花费降了 16.7%，若宠物价格不动，宠物相对购买力会**变贵 20%** —— 攒同一件商品要多付出两成抽奖次数，这本身就是对赚星积极性的打击。因此价格按下式联动：

```
新价格 = 旧价格 × (新抽奖期望 / 旧抽奖期望) = 旧价格 × 0.83
```

| 类别 | 调整前 | 调整后 |
|---|---|---|
| 喂口水 / 打扫小窝 | 3 / 4 ⭐ | 3 / 3 ⭐ |
| 小零食 / 梳毛洗澡 | 5 / 6 ⭐ | 4 / 5 ⭐ |
| 小蛋糕 / 陪它玩 | 8 / 10 ⭐ | 7 / 8 ⭐ |
| 正餐 | 12 ⭐ | 10 ⭐ |
| 装扮 24 件 | 15-72 ⭐ | 12-58 ⭐ |

价格用乘算关系而非拍脑袋：这样"攒 N 次抽奖换一件商品"的体感在调价前后保持一致。

### 积分系统重设计（v3.0.0）

抽奖价格不动，因此只能调收入侧。重设计的出发点是三个**结构性失衡**，而不是"数字不好看"：

| 失衡 | 原状 | 后果 |
|---|---|---|
| 最省力的动作收益最高 | 待办 5-10⭐ vs 打卡 3⭐ | 勾一个复选框赚的比坚持打卡多，待办退化成抽奖燃料 |
| 高价值行为无额外回报 | 完成计划只结算已有的打卡积分 | 21 次的难计划和 3 次的易计划终点等价，没有理由选难的 |
| 日目标不可达 | 目标 60⭐，实际日产出约 38⭐ | 首页唯一的进度条长期显示"没做到"，禀赋效应变成挫败 |

**改动**：

| 项目 | 原 | 新 | 理由 |
|---|---|---|---|
| 完成待办 | 5-10⭐ | **3-6⭐** | 收窄。仍值得做，但不再是最优解 |
| 完成计划 | 次数×3 | 次数×3 **+ 10⭐** | 一次性"你完成了某件事"的支付，让难计划有额外价值 |
| 复习 | 1-6⭐ | 1-6⭐ **+ 当日第 3/5/8 张各 +2/3/5⭐** | 奖励持续性而非数量，按日历日计，无法一次性刷满 |
| 每日目标 | 60⭐ | **40⭐** | 活跃用户日产出 37-42⭐，可达但需努力 |
| 打卡 | 3⭐ | 3⭐（不变） | 最稳定的习惯锚点，不该被任何东西盖过 |

**日均收支**（典型活跃使用：2 计划打卡 + 2 待办 + 3 记录 + 5 复习）：

| | 旧 | 新 |
|---|---|---|
| 日均收入 | 37.5⭐ | 39.5⭐ |
| 日均支出 | 32.4⭐ | 32.4⭐（抽奖 3 次 + 宠物 2 次） |
| 结余率 | 13.6% | **18.2%** |

结余率上升是**有意保留**的缓冲：早期用户往往比典型值更活跃，如果精确对齐到零，任何高频使用者都会立刻见底，而见底比结余更能摧毁动力。但 18% 也是上限——再高就是货币贬值，星星堆积会同时削弱抽奖和宠物两个出口。

**这一节的诚实前提**：联动计算假设抽奖次数不变。实际上抽奖变便宜后用户可能抽得更多次，真实支出未必下降。所以这是维持相对购买力，不是保证收支平衡。

无"谢谢惠顾"安慰奖——18 项全是真奖，中奖的悬念全部由头奖的稀有度承担。

**异常处理**：
- 奖池为空 → 提示先添加奖项
- 星星不足 → **不再拦截**，正常抽奖并扣成负数

### 3. 任务计划（🎯）

用于有明确目标次数的重复性计划，如"读书 30 次""跑步 100 次"。

| 功能 | 说明 |
|---|---|
| **目标 + 打卡** | 设定目标次数，每次打卡 +1 计数、+3 星 |
| **星星进度条** | 目标梯度效应缓动，越接近目标走得越快 |
| **每日限一次** | 数据库唯一索引强制去重，重复点击无法刷星 |
| **每日自动重置** | 跨零点后按钮自动恢复可点，界面无需重启 |
| **完成归档** | 达成目标自动转入"已完成"，发放该计划自己设定的完成奖励（默认 10 星，上限 10 星） |
| **打卡历史** | 按计划留存全部打卡记录 |

**防刷设计**：同一计划同一天只能打卡一次，由数据库唯一索引 `(planId, dayKey)` 强制保证，而非应用层判断。这意味着即使并发点击或数据库逻辑被绕过，星星也无法被刷取。

**自填奖励有上限**（v1.5.1，v1.6.0 调整）：计划完成奖励与待办奖励都由用户自己填写，而**用户可以自己填的奖励，就是用户可以自己印的货币**——一次点击能值 500 星的话，其他所有赚星途径都变成噪音，宠物这个星星出口也会被瞬间买空。

v1.6.0 起，计划完成奖励的上限**随目标次数缩放**：

| 项 | 规则 | 例子（目标 10 次） |
|---|---|---|
| 默认完成奖励 | 目标次数 × 3 星 | 30 星 |
| 完成奖励上限 | 目标次数 × 5 星 | 50 星 |
| 待办奖励 | 固定上限 10 星（无目标次数可依） | 10 星 |

上限必须**随目标次数缩放**，否则一个 2 次的计划会比一个 30 次的计划更值钱 —— 那正好把"目标次数设大一点更划算"的激励拧反了。

上限在**发放路径**上强制执行，而不只是在输入框里：早于该上限存在的旧数据行仍可能存着超限值，只在 UI 拦住等于没拦。撤销待办时退还的也是钳制后的同一个值，保证"发了多少退多少"，不会把余额打成负数。

顺带修掉一个承诺不兑现的问题：编辑计划时叫"完成奖励⭐"、列表上写"完成 +N⭐"，但完成时实际发的是硬编码常量（20+3），与用户填的值完全无关。现在完成时发放该计划自己设定的奖励。

**"今天"是一个流，不是一个值**（v1.4.1 修复）：打卡按钮曾把当天日期读一次后缓存起来，而界面数据只在数据库**写入**时才刷新。零点那一刻数据库没有任何写入，于是昨天的日期活到了第二天，昨天打过卡的计划永远停在"今日已打卡 ✓"的灰态，直到某个无关写入碰巧刷新它。现在把日键做成独立的数据流（每 30 秒重读一次当天日期并去重下发），打卡集合、首页"今日星星"、复习到期队列全部由它派生——**日子的推进不需要任何数据变动来触发**。轮询而非精确定时到零点，是因为时钟本身也会跳（手动改时间、跨时区旅行），只有重新读取才追得上。

### 4. 待办清单（✅）

| 功能 | 说明 |
|---|---|
| **三档优先级** | 高 / 中 / 低，自动排序，高优先级始终在前 |
| **一键完成** | 单击复选框即划线完成，+5 星（每条可单独设置，上限 10 星） |
| **撤销退还** | 重新打开会退还当初发放的星星，账目始终对得上 |
| **已完成列表** | 折叠查看，可重新打开或删除 |
| **完成历史** | 记录精确到分钟 |

**单次点击即可完成**是刻意设计：最小可行动作上的任何摩擦，都是习惯中断的主要原因。完整完成一项待办的流程是"点一下复选框"，没有二次确认。

### 5. 吃什么（🍽）

| 功能 | 说明 |
|---|---|
| **随机抽签** | 缓解选择困难，约 24 步减速滚动后揭晓 |
| **食物池管理** | 增删改，含名称、分类、emoji |
| **首次启动预置** | 内置 61 道家常菜，覆盖蛋与豆制品、猪牛、鸡鸭、汤羹、河海鲜、素菜、主食硬菜 |

**"分类"字段在这里承载的是当季信息**（例如 `6-8月`、`全年（土豆耐储）`、`9-12月（秋冬白萝卜）`），抽中后直接显示在菜名下方。这样抽签结果不只是"吃什么"，还顺带告诉家长这道菜现在当不当季——同一道菜在不同月份，抽到的其实是一样的，但看到时令提示更容易做出"今天合适"的判断。

结果由用户主动点击按钮产生，而非自动弹出——这让结果读作"我的决定"而非"被强加的结果"，自主感（autonomy）是内在动机的核心要素。

### 6. 复习（🧠）

| 功能 | 说明 |
|---|---|
| **录入学习内容** | **问题与答案分两个输入框**；问题换行或句号自动拆成多张小卡，每行 ≤ 80 字 |
| **答案可选** | 留空则复习时只回看问题；多行答案按行序与多行问题一一对应 |
| **难度分级** | 简单 / 中等 / 有难度 —— 同时影响星星奖励与初始复习密度 |
| **今日复习队列** | 只显示到期的卡片，**按录入时间从旧到新排序**，逾期项自动顺延保留 |
| **自测式复习** | 点击后**先显示问题让你回忆** → 揭晓答案 → 三档自评（想起来了 / 有点模糊 / 完全忘了） |
| **自适应间隔（SM-2）** | 每张卡带自己的易记因子，记得好则乘性拉长，忘了则退回并收紧 |
| **出师机制** | 间隔达到 21 天即标记"已出师 🎓"，退出每日队列，不再占用注意力 |
| **变量奖励** | 完成复习有约 15% 概率触发"记忆闪光"，星星翻倍 |
| **内容管理** | 头部统计连胜与今日进度；「全部内容」查看轮次、遗忘次数、下次到期 |

**为什么是"自测"而不是勾选"我看过了"**：这是本功能最关键的一处设计。多数复习类应用的做法是"点一下表示已复习"，但它几乎无效——刚看过一句话再认出来，产生的是**流畅感**，而大脑会把流畅感误认成已经掌握（流畅性错觉）。真正让记忆固化的是在看到答案**之前**主动把它提取出来的那个吃力动作，也就是**测验效应**（testing effect）：Roediger & Karpicke (2006) 在等时对比下发现，检索练习对长期保持的效果约为重复阅读的两倍。

因此流程是三段：**遮盖 → 回忆 → 揭晓自评**。自评三档必须诚实才有意义，于是奖励设计成"忘了也给 1 星"——如果把失败设为零收益，用户会为了保护星星一律点"想起来了"，测量工具就变成了谎言发生器，下游排程随之失真。

**问题与答案必须是两个字段**（v1.6.0）：此前一张卡只有一段文本，于是回忆阶段只显示"闭上眼睛，试着把它说出来"，揭晓阶段又把同一段话原样显示出来——**用户没有任何东西可提取，也没有任何东西可核对**。测验效应依赖"看到答案之前主动提取"这个动作，而这个动作要求问题与答案是两件不同的事。现在两者分开存储与展示：回忆阶段显示问题，揭晓阶段显示答案。答案可留空（留空则退化为只回看问题），多行答案按行序与多行问题对应——按位置配对而非按内容匹配，因为内容匹配在任何一次重排后都会悄悄接错答案，那比没有答案更糟。

**为什么用 SM-2 而不是固定间隔表**：固定表（1/2/4/7/15/30）默认所有知识一样难，事实上"光合作用的场所"和"线粒体与叶绿体的区别"衰减速度不同。SM-2 给每张卡维护一个**易记因子**——回忆成功则下一次按倍数拉长，失败则证明它比预估的难，因子下降、回来得更密。排程随之适应学习者，而不是让学习者适应表格。

对经典算法做了三处针对场景的修改：①第二轮间隔取 3 天而非原文的 6 天（原文面向成人外语密集卡片，6 天对小学知识往往过头，而"过头"的代价是彻底重学）；②失败只重置连续成功计数，不动易记因子（一次遗忘已经付出代价，再降因子会让卡片永远困在每日队列里，把复习变成惩罚）；③出师以**间隔长度**（≥21 天）定义而非固定轮数 —— "出师"应该意味着保持得够稳，而间隔长度是唯一可观测的代理指标。

三条仍然成立的取舍：

- **按天而不是按小时**。复习习惯挂在"晚饭后"这样的时间点上，而不是某个时钟偏移；以天为单位同时天然保证同一天内不能重复复习同一条，不存在刷分漏洞。
- **晚复习不受惩罚**。下一次间隔从"实际完成复习的那天"起算，而不是原定到期日。补上就行，不倒扣——用忘记的东西惩罚自己，是这个功能最容易劝退人的写法。
- **排序按录入时间而非到期时间**。最早学的东西离被遗忘最近，它才是今天最值得先复习的那一条。

另有两条新增约束：**单卡 ≤ 80 字**（超过建议拆分）——超过工作记忆容量就无法被"回忆"，只会被"认出来"；**天粒度 + 诚实自评**，二者共同保证同一张卡一天不可能产出两次收益。

### 7. 宠物（🐾）

| 功能 | 说明 |
|---|---|
| **状态系统** | 饱腹（约 20 小时耗尽）、心情（约 40 小时耗尽），随时间实时衰减，离线也在走 |
| **八种表情** | 开心 / 满足 / 发呆 / 有点饿 / 眼巴巴 / 委屈 / 睡着了 / 吃得香，由状态自动推导 |
| **七种照顾** | 喂水 3⭐ / 小零食 5⭐ / 打扫小窝 4⭐ / 梳毛洗澡 6⭐ / 小蛋糕 8⭐ / 陪它玩 10⭐ / 正餐 12⭐ |
| **五段形态** | 蛋 → 幼崽（1 次）→ 小伙伴（30 次）→ 守护兽（90 次）→ 星辰伙伴（240 次） |
| **等级（无上限）** | 每照顾 20 次升一级，Lv.1 起，**永远有下一级** |
| **装扮商店** | 4 个部位（头顶 / 脸上 / 脖子 / 身后）共 24 件，15–72⭐，分常见 / 稀有 / 传说三档，买断后随时免费更换 |
| **摆正装扮** | 任意已戴上的装扮可直接拖动对齐，位置按**每件**分别记忆；可单件复位或全部复位 |
| **对话系统** | 每种表情 3 句轮换文案，避免"录音式"重复感 |
| **起名** | 12 字以内自定义名字（免费，用于建立归属） |

**为什么不封顶（v1.5.0 的核心改动）**：旧版在照顾 60 次后就走到"已经是最终形态"，此后再无任何反馈——**一个被玩通关的宠物就不再是打开应用的理由**。现在分两条线：形态（5 个可见里程碑，负责早期成就感）与等级（每 20 次照顾升一级，**没有上限**）。哪怕到了最终形态，等级仍会继续增长，屏幕上永远有"下一次"的存在。

**为什么最便宜的动作只要 3 颗星**：预算紧张的日子也必须能问候它，否则宠物就从伙伴变成了债主。喂水、打扫这类低价动作的存在，是为了让"今天收益很少"的用户仍能完成一次照顾而不必心疼。

**为什么装扮可以自己拖**：emoji 字形各自带着不同的内边距与基线，同一个锚点不可能同时对齐礼帽和光环——这不是参数没调好，而是**没人能从代码里判断什么叫"正"**。与其继续猜，不如让看得到屏幕的人自己定。因此在"摆正装扮"模式下按住任意装扮即可拖动，松手持久化；默认值也已全部改为相对画布中心的坐标（旧写法是按边缘对齐再往上推，帽子会被推出画布导致偏移，无法靠忍耐修正）。

**为什么要在学习类应用里养宠物**：它是星星的**出路**。前几个功能负责产出星星，但如果星星只能换抽奖，积分很快会因缺少可积累的目标而通胀、失去驱动力。宠物的作用是把已经花掉的努力沉淀成一个**会持续存在的东西**：

- **禀赋效应 / IKEA 效应**：亲手喂养和装扮之后，它对用户的价值高于所花星星的总和，于是用户会为了**保护**它而行动。
- **蔡格尼克效应**：饥饿条是未完成事件，会产生轻微的心理张力直到被关闭。饥饿状态会被文案放大（"看我这么可爱，忍心吗？"）。
- **损失厌恶**：宠物不会死（把惩罚写成死亡会毒化整个循环），但会 visibly 蔫下去。避免损失比争取等量收益更能驱动行为。

三条刻意设计：**成长只由照顾次数驱动**，与花了多少星星无关，所以连续买最贵的零食并不能加速进化——由"到场次数"决定，是为了保护这个功能的初衷；**星星不够时它反过来撒娇**（"再去赚点星星回来嘛"），把挫败感转成动机而不是弹报错；**宠物状态完全独立于星星账本**，它既不考核也不惩罚，是星星的去向而不是新的任务。

### 积分清零（家长功能，v4.1.0）

首页最底部有一个低调的「重置积分」按钮，点击后要求输入口令，匹配则把积分归零。

**为什么放在首页最末尾**：这是个不可撤销的破坏性操作。放在余额旁边意味着好奇的手指一次就能点到；放在列表末尾意味着要先滑到底、再输入口令，两道门槛。

**为什么口令用明文比较**：这个口令**不是安全控制**，而是防误触。应用纯本地运行，字符串就打包在 APK 里，任何反编译的人都能读到——把它伪装成秘密是虚假的安心感。它真正买到的是它该买的东西：两岁小孩猜不到，误触也擦不空一个月。

**正负积分一视同仁**：余额 = 账本所有 `delta` 之和，所以清空账本即清零，与之前是正还是负无关。这同时会抹掉累计欠账——而这正是"清零"应有的含义；如果清完还剩 -30，那就不叫清零。

**清零不影响努力记录**：打卡、待办、复习各自独立成表，不依赖星星账本。被清掉的只有星星本身，以及星星的流水显示。

口令校验在 ViewModel 而非 Repository：口令不对时不产生任何数据库写入。

单测 `StarResetTest`（3 项）覆盖：精确匹配通过；12 种近似输入被拒（缺数字、多数字、含空格、换行、全角数字、拼音替代等）；校验不修改入参。

## 四、星星经济

### 收入项

| 行为 | 星星 | 备注 |
|---|---|---|
| 计划打卡 | +3（每次，上限 5） | 每日一次，可多计划叠加 |
| 完成计划 | **目标次数 × 3 + 10** | 达成额外 +10，一次性 |
| 完成待办 | +0~+6（默认 4） | 自定义，上限 6 |
| 记录新学内容 | +2~+4 | 简单 2 / 中等 3 / 有难度 4 |
| 完成一次复习 | +1~+6 | 按难度 × 自评；约 15% 概率翻倍 |
| **当日第 3 / 5 / 8 张复习** | **额外 +2 / +3 / +5** | 按日历日计，一次性 |
| 首次启动礼包 | +10 | 禀赋起点 |

**完成计划为什么按目标次数缩放**：完成奖励在创建计划时就可编辑（默认 63⭐ = 21 × 3），列表页也显示"完成 +N⭐"。若结算时付一个写死的常量，这两个承诺都是假的。达成额外 +10⭐ 是"你完成了某件事"的支付 —— 否则 21 次的难计划和 3 次的易计划终点完全等价，没有理由选难的。

**复习连击为什么按日历日计**：奖励的是持续性而非数量，且用 `review_log` 表统计而非内存计数，所以进程被杀也不丢、也无法靠一次会话刷满。

**待办上限为什么收到 6**：原先是 10。那时勾一个复选框（5–10⭐）比坚持打卡（3⭐）赚得多，待办退化成抽奖燃料 —— 应用里最省力的动作成了最优收入来源。待办仍值得做，但不再是最优解。

### 支出项

**抽奖**：按所中奖项定价（1–30⭐），期望花费 **7.82⭐**（按当前 18 项权重与价格精确计算）。星星不足**不拦截**，直接扣成负数。

**宠物**：照顾动作 3–10⭐，装扮 12–60⭐（24 件）。**余额不足时拒绝消费** —— 抽奖可以欠账，宠物不行。欠账若能继续买东西，负余额就没有尽头。

### 定价校准

约 **1.5 次打卡（5⭐）≈ 1 次抽奖（7.82⭐）**；攒一件普通装扮（20⭐）约需 2.6 次抽奖，最贵的装扮（60⭐）约需 7.7 次。

这个比例是刻意设计的：奖励太难获得就不再是奖励。定价过低则抽奖失去分量感，定价过高则闭环断裂、攒不到就放弃。

### 日目标

目标 **40⭐**，禀赋起点 10⭐。

原目标是 60⭐ 而实际日产出约 38⭐ —— 活跃用户也永远达不到，首页唯一的进度条长期显示"没做到"，禀赋效应直接变成挫败。40⭐ 高于轻松的一天、低于认真的一天，够得着但需要努力。

### 账本设计

`star_ledger` 表采用 **append-only** 模型：

- 每次变动记录 `delta`、`balanceAfter`、`reason`、`createdAt`
- 当前余额 = 所有 delta 求和，永远可从历史重算校验
- 撤销待办写入负 delta 而非删除记录，**账目始终可审计**
- 唯一例外是**家长手动清零**（口令保护），直接清空账本 —— 见上文 v4.1.0

## 五、心理学机制

每个机制在 `core/RewardEngine.kt` 中均标注了理论出处，确保后续修改不会破坏设计意图。

| 理论 | 提出者 | 实现方式 |
|---|---|---|
| **可变比率强化** | Skinner | 加权随机抽奖 + 减速揭晓动画，奖励频率不可预测 |
| **目标梯度效应** | Kivetz | 进度条用幂曲线缓动（1-(1-r)^2.2），末端视觉加速 |
| **禀赋效应** | Nunes & Drèze | 每日目标非零起始；首启赠送 10 星先体验完整循环 |
| **损失厌恶 / 连贯性** | Kahneman | 连续打卡天数显式追踪并展示，破坏连胜读作"损失" |
| **自我决定理论** | Deci & Ryan | 文案肯定能力与自主，零内疚设计 |
| **蔡格尼克效应** | Zeigarnik | 未完成计划常驻首页，保持适度注意力张力 |
| **快速早期胜利** | — | 幂律等级曲线，前期升级快 |

### 等级曲线

等级阈值采用**幂律增长**（`60 × level^1.613`，上限 100 级）：前期升级快以快速建立习惯，后期需要持续投入才有意义。

**技术说明**：阈值由闭式公式预计算成表，等级通过二分查找定位。闭式求逆（`pow` + `toInt`）在整数截断下无法自洽——每个等级边界回退一级，导致每次升级瞬间进度条跳到 100%。该问题在单元测试中被发现并修复。

| `pet` | 宠物单条记录（id 固定为 1） | 主键即 id |
| `star_ledger` | 星星账本 | `createdAt` |

数据库版本 **v11**，每次升级都是写入式迁移（手写 SQL），老用户升级保留全部星星、计划、连续记录与复习进度。`fallbackToDestructiveMigration` 仅作为未知版本路径的最后兜底。

`review_items` 的到期时间存的是 `yyyy-MM-dd` 日期键而非时间戳：ISO 日期串的字典序等于时间序，因此"是否到期"在 SQL 里就是一个 `<=` 比较，查询时不需要任何时区换算。

全部 UI 状态经 Room `Flow` 驱动，DAO 变更自动刷新界面，无手动刷新逻辑。

## 八、已知局限

诚实列出当前实现的不足，便于评估是否需要改进。

### 功能性缺陷


**2. 无数据导出/备份接口**

数据仅存本地 SQLite，无导出功能。卸载应用即丢失。

**3. release 使用 debug keystore 签名**

仅为开箱可安装。正式分发前必须配置真实签名配置。

### 验证范围限制

**已在真机验证过**（v4.0.1 及之前的迭代）。这个过程暴露过一次严重问题：v4.0.0 的"权重自动均化"代码实际上从未写进文件，而纯函数单测全绿、编译通过、构建成功 —— 三道验证全部没能发现它。**纯函数测试全绿不等于功能接线正确**，此后所有涉及调用链接入的改动都额外 grep 确认目标函数体内确实出现了新调用。

仍未真机验证的部分：v4.1.0 新增的积分清零（含负余额场景）、抽奖刮开交互的手感。

### 潜在优化点

- 计划打卡未做"补卡"机制，漏打卡即中断当天进度
- 抽奖滚动为固定 70ms 循环，未按星星余额动态调整期待感
- 长休息阶段需手动切换，普通用户可能只使用 25/5 两阶段而忽略 15 分钟长休息
- 积分清零口令以明文打包在 APK 内，可被反编译读取；它是防误触而非安全控制
- 连续抽到同一具体小奖的概率约 7%（前三项合计 46% 的必然结果），可通过下调前三项占比缓解

## 九、设计决策记录

记录几个非显而易见的决策及其原因，便于后续维护时理解。

| 决策 | 原因 |
|---|---|
| 星星账本用 append-only 而非余额字段 | 余额可从历史重算，异常可被发现；直接改余额字段则无法追溯 |
| 打卡去重放在数据库唯一索引 | 应用层判断在并发下不可靠；唯一索引是最后防线 |
| 抽奖星星从"抽中的奖项"扣除 | 先选定再扣费，保证扣费金额与实际所得奖励一致 |
| 短休息奖励压到 2 星 | 防止奖励结构反向激励"刷休息"而非工作 |
| 首页先显示等级而非任务 | 先定向再行动，避免任务列表带来的压迫感 |
| 进度条末端加速 | 目标梯度效应：最后阶段是放弃率最高点，需强化冲刺感 |
| 撤销待办退还星星 | 保证账本忠实反映"已获得"，而非"当前持有" |
| 「今天」由数据流下发而非读一次缓存 | 零点没有数据库写入，缓存的日期会跨天存活，打卡状态便永不复位 |
