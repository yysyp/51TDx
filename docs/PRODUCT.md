# 51TDx 产品功能文档

> 版本：v1.5.0 ｜ 包名：`com.ran.app` ｜ minSdk 26 / target 34
> 技术栈：Kotlin 2.0.20 + Jetpack Compose (Material 3) + Room 2.6.1 + MVVM

---

## 一、产品定位

51TDx 是一个**自我激励工具**，不是任务管理器。

大多数待办应用的激励方式是"完成了一项"这样一句平淡的反馈，完成之后就没有然后了。51TDx 的设计目标是把所有行为接入同一个奖励经济系统，让每一次行动都能兑换到实际的东西——一杯咖啡、一集剧、一个下午的自由。

### 核心闭环

```
行动（打卡 / 完成任务 / 完成复习）
   ↓ 自动发放
获得星星 ⭐
   ↓ 攒够后消耗
抽奖 / 兑换奖励
   ↓ 拿到真实奖励
产生下一次行动的动机
```

这条链路是整个应用的骨架。**四个功能模块不是并列的工具，而是同一套经济系统的不同入口**——打卡攒的星能抽奖，完成待办也能抽奖。因此任何一个模块都不是死胡同，用户无论从哪个功能进来，都在推进同一条进度。

### 设计原则

| 原则 | 落地方式 |
|---|---|
| 奖励必须够得着 | 定价校准为约三次打卡换一次抽奖 |
| 永不制造愧疚 | 全部文案为能力肯定式，无指责、无失败状态 |
| 最小动作零摩擦 | 完成待办只需单击复选框 |
| 努力必须被看见 | 每个模块都有历史记录页 |
| 账目必须可追溯 | 星星变动采用 append-only 账本 |

## 三、功能模块详解

### 1. 首页仪表盘

打开应用首先看到渐变等级卡，而非任务列表。信息顺序是刻意的：**先回答"我在哪"，再回答"能做什么"**，让用户保持方向感而非被任务淹没。

| 元素 | 内容 |
|---|---|
| **等级卡** | Lv 等级、星星余额、连续打卡天数、水平进度条（暖色渐变） |
| **今日目标** | 按当日获星进度填充，起始即有非零进度 |
| **今日概览** | 今日星星 / 待办数 / 进行中计划数，三个圆形计数 |
| **进行中计划** | 最多显示 3 项，超出显示"还有 N 项…" |

**文案策略**：全部为能力肯定式。例如进度过半显示"进度过半了，继续保持"，而非"还有一半没完成"。基于自我决定理论，愧疚感是行为改变的最大阻力，会导致用户直接放弃应用。

---

### 2. 抽奖（🎰）

用可变比率强化（Skinner）机制驱动：奖励频率不可预测，因此行为能长期维持。

| 功能 | 说明 |
|---|---|
| **加权随机** | 每个奖项有独立权重字段，权重越高越易被抽中 |
| **星星定价** | 每个奖项单独定价，花费从**抽中的那个**奖项扣除 |
| **大奖判定** | 动态计算：花费 ≥ 池内均价的 1.8 倍自动标记为大奖 |
| **奖项管理** | 完整增删改，含名称、描述、emoji、权重、星星价 |
| **中奖记录** | 最近 50 条，大奖带高亮"大奖"标签 |

**减速滚动动画**是核心细节：约 28 步逐步减速（55ms 起，每步 ×1.18 递增，上限 260ms），先快后慢保留悬念。若瞬间揭晓结果，随机奖励的激励强度会大幅衰减——这是可变比率强化机制的必要配套，而非纯装饰。

**首次启动内置 23 个奖项**，按价值分三档，越贵权重越低（总权重 220）：

- **小额高频**（3-18 星，权重 7-24）：小水果1份(24/3)、小零食1份(22/4)、一杯饮料(20/5)、屏幕时间+15分钟(18/5)、免家务1次(14/8)、屏幕时间+30分钟(13/10)、冰淇淋券1张(12/8)、屏幕时间+1小时(8/18)、点外卖(7/18)
- **安慰奖**：谢谢惠顾(10 权重 / **0 星**)——抽中不扣星星也不发奖，保留"这次没中"的随机性，又不会造成损失
- **中档**（12-35 星，权重 3-11）：零花钱+5(11/12)、奶茶券1张(10/12)、周末晚睡15分钟(9/12)、自选周末午餐(9/15)、零花钱+10(7/22)、邀请同学来家玩(5/25)、买一本想要的书(5/28)、一场电影(4/30)、零花钱+15(4/32)、吃大餐(3/35)
- **大奖**（42-55 星，权重 1-2）：零花钱+20(2/42)、周末半日游(2/50)、中等玩具(1/55)

池内均价约 19.5 星，因此花费 ≥ 35 星的 3 项会被自动标记为"大奖"，中大奖概率约 2.3%——低频但够响，正反馈梯度完整。

**异常处理**：
- 奖池为空 → 提示先添加奖项
- 星星不足 → 提示去完成任务赚星星（不产生负余额）

### 3. 任务计划（🎯）

用于有明确目标次数的重复性计划，如"读书 30 次""跑步 100 次"。

| 功能 | 说明 |
|---|---|
| **目标 + 打卡** | 设定目标次数，每次打卡 +1 计数、+3 星 |
| **星星进度条** | 目标梯度效应缓动，越接近目标走得越快 |
| **每日限一次** | 数据库唯一索引强制去重，重复点击无法刷星 |
| **每日自动重置** | 跨零点后按钮自动恢复可点，界面无需重启 |
| **完成归档** | 达成目标自动转入"已完成"，额外 +20 星 |
| **打卡历史** | 按计划留存全部打卡记录 |

**防刷设计**：同一计划同一天只能打卡一次，由数据库唯一索引 `(planId, dayKey)` 强制保证，而非应用层判断。这意味着即使并发点击或数据库逻辑被绕过，星星也无法被刷取。

**"今天"是一个流，不是一个值**（v1.4.1 修复）：打卡按钮曾把当天日期读一次后缓存起来，而界面数据只在数据库**写入**时才刷新。零点那一刻数据库没有任何写入，于是昨天的日期活到了第二天，昨天打过卡的计划永远停在"今日已打卡 ✓"的灰态，直到某个无关写入碰巧刷新它。现在把日键做成独立的数据流（每 30 秒重读一次当天日期并去重下发），打卡集合、首页"今日星星"、复习到期队列全部由它派生——**日子的推进不需要任何数据变动来触发**。轮询而非精确定时到零点，是因为时钟本身也会跳（手动改时间、跨时区旅行），只有重新读取才追得上。

### 4. 待办清单（✅）

| 功能 | 说明 |
|---|---|
| **三档优先级** | 高 / 中 / 低，自动排序，高优先级始终在前 |
| **一键完成** | 单击复选框即划线完成，+5 星（每条可单独设置） |
| **撤销退还** | 重新打开会退还当初发放的星星，账目始终对得上 |
| **已完成列表** | 折叠查看，可重新打开或删除 |
| **完成历史** | 记录精确到分钟 |

**单次点击即可完成**是刻意设计：最小可行动作上的任何摩擦，都是习惯中断的主要原因。完整完成一项待办的流程是"点一下复选框"，没有二次确认。

### 5. 吃什么（🍽）

| 功能 | 说明 |
|---|---|
| **随机抽签** | 缓解选择困难，约 24 步减速滚动后揭晓 |
| **食物池管理** | 增删改，含名称、分类、emoji |
| **首次启动预置** | 内置 61 道家常菜，覆盖蛋与豆制品、猪牛、鸡鸭、汤羹、河海鲜、素菜、主食硬菜 |

**"分类"字段在这里承载的是当季信息**（例如 `6-8月`、`全年（土豆耐储）`、`9-12月（秋冬白萝卜）`），抽中后直接显示在菜名下方。这样抽签结果不只是"吃什么"，还顺带告诉家长这道菜现在当不当季——同一道菜在不同月份，抽到的其实是一样的，但看到时令提示更容易做出"今天合适"的判断。

结果由用户主动点击按钮产生，而非自动弹出——这让结果读作"我的决定"而非"被强加的结果"，自主感（autonomy）是内在动机的核心要素。

### 6. 复习（🧠）

| 功能 | 说明 |
|---|---|
| **录入学习内容** | 写下今天学到的东西；换行或句号自动拆成多张小卡；每行 ≤ 80 字 |
| **难度分级** | 简单 / 中等 / 有难度 —— 同时影响星星奖励与初始复习密度 |
| **今日复习队列** | 只显示到期的卡片，**按录入时间从旧到新排序**，逾期项自动顺延保留 |
| **自测式复习** | 点击后先**遮住答案**促回忆 → 揭晓 → 三档自评（想起来了 / 有点模糊 / 完全忘了） |
| **自适应间隔（SM-2）** | 每张卡带自己的易记因子，记得好则乘性拉长，忘了则退回并收紧 |
| **出师机制** | 间隔达到 21 天即标记"已出师 🎓"，退出每日队列，不再占用注意力 |
| **变量奖励** | 完成复习有约 15% 概率触发"记忆闪光"，星星翻倍 |
| **内容管理** | 头部统计连胜与今日进度；「全部内容」查看轮次、遗忘次数、下次到期 |

**为什么是"自测"而不是勾选"我看过了"**：这是本功能最关键的一处设计。多数复习类应用的做法是"点一下表示已复习"，但它几乎无效——刚看过一句话再认出来，产生的是**流畅感**，而大脑会把流畅感误认成已经掌握（流畅性错觉）。真正让记忆固化的是在看到答案**之前**主动把它提取出来的那个吃力动作，也就是**测验效应**（testing effect）：Roediger & Karpicke (2006) 在等时对比下发现，检索练习对长期保持的效果约为重复阅读的两倍。

因此流程是三段：**遮盖 → 回忆 → 揭晓自评**。自评三档必须诚实才有意义，于是奖励设计成"忘了也给 1 星"——如果把失败设为零收益，用户会为了保护星星一律点"想起来了"，测量工具就变成了谎言发生器，下游排程随之失真。

**为什么用 SM-2 而不是固定间隔表**：固定表（1/2/4/7/15/30）默认所有知识一样难，事实上"光合作用的场所"和"线粒体与叶绿体的区别"衰减速度不同。SM-2 给每张卡维护一个**易记因子**——回忆成功则下一次按倍数拉长，失败则证明它比预估的难，因子下降、回来得更密。排程随之适应学习者，而不是让学习者适应表格。

对经典算法做了三处针对场景的修改：①第二轮间隔取 3 天而非原文的 6 天（原文面向成人外语密集卡片，6 天对小学知识往往过头，而"过头"的代价是彻底重学）；②失败只重置连续成功计数，不动易记因子（一次遗忘已经付出代价，再降因子会让卡片永远困在每日队列里，把复习变成惩罚）；③出师以**间隔长度**（≥21 天）定义而非固定轮数 —— "出师"应该意味着保持得够稳，而间隔长度是唯一可观测的代理指标。

三条仍然成立的取舍：

- **按天而不是按小时**。复习习惯挂在"晚饭后"这样的时间点上，而不是某个时钟偏移；以天为单位同时天然保证同一天内不能重复复习同一条，不存在刷分漏洞。
- **晚复习不受惩罚**。下一次间隔从"实际完成复习的那天"起算，而不是原定到期日。补上就行，不倒扣——用忘记的东西惩罚自己，是这个功能最容易劝退人的写法。
- **排序按录入时间而非到期时间**。最早学的东西离被遗忘最近，它才是今天最值得先复习的那一条。

另有两条新增约束：**单卡 ≤ 80 字**（超过建议拆分）——超过工作记忆容量就无法被"回忆"，只会被"认出来"；**天粒度 + 诚实自评**，二者共同保证同一张卡一天不可能产出两次收益。

### 7. 宠物（🐾）

| 功能 | 说明 |
|---|---|
| **状态系统** | 饱腹（约 20 小时耗尽）、心情（约 40 小时耗尽），随时间实时衰减，离线也在走 |
| **八种表情** | 开心 / 满足 / 发呆 / 有点饿 / 眼巴巴 / 委屈 / 睡着了 / 吃得香，由状态自动推导 |
| **七种照顾** | 喂水 3⭐ / 小零食 5⭐ / 打扫小窝 4⭐ / 梳毛洗澡 6⭐ / 小蛋糕 8⭐ / 陪它玩 10⭐ / 正餐 12⭐ |
| **五段形态** | 蛋 → 幼崽（1 次）→ 小伙伴（30 次）→ 守护兽（90 次）→ 星辰伙伴（240 次） |
| **等级（无上限）** | 每照顾 20 次升一级，Lv.1 起，**永远有下一级** |
| **装扮商店** | 4 个部位（头顶 / 脸上 / 脖子 / 身后）共 24 件，15–72⭐，分常见 / 稀有 / 传说三档，买断后随时免费更换 |
| **摆正装扮** | 任意已戴上的装扮可直接拖动对齐，位置按**每件**分别记忆；可单件复位或全部复位 |
| **对话系统** | 每种表情 3 句轮换文案，避免"录音式"重复感 |
| **起名** | 12 字以内自定义名字（免费，用于建立归属） |

**为什么不封顶（v1.5.0 的核心改动）**：旧版在照顾 60 次后就走到"已经是最终形态"，此后再无任何反馈——**一个被玩通关的宠物就不再是打开应用的理由**。现在分两条线：形态（5 个可见里程碑，负责早期成就感）与等级（每 20 次照顾升一级，**没有上限**）。哪怕到了最终形态，等级仍会继续增长，屏幕上永远有"下一次"的存在。

**为什么最便宜的动作只要 3 颗星**：预算紧张的日子也必须能问候它，否则宠物就从伙伴变成了债主。喂水、打扫这类低价动作的存在，是为了让"今天收益很少"的用户仍能完成一次照顾而不必心疼。

**为什么装扮可以自己拖**：emoji 字形各自带着不同的内边距与基线，同一个锚点不可能同时对齐礼帽和光环——这不是参数没调好，而是**没人能从代码里判断什么叫"正"**。与其继续猜，不如让看得到屏幕的人自己定。因此在"摆正装扮"模式下按住任意装扮即可拖动，松手持久化；默认值也已全部改为相对画布中心的坐标（旧写法是按边缘对齐再往上推，帽子会被推出画布导致偏移，无法靠忍耐修正）。

**为什么要在学习类应用里养宠物**：它是星星的**出路**。前几个功能负责产出星星，但如果星星只能换抽奖，积分很快会因缺少可积累的目标而通胀、失去驱动力。宠物的作用是把已经花掉的努力沉淀成一个**会持续存在的东西**：

- **禀赋效应 / IKEA 效应**：亲手喂养和装扮之后，它对用户的价值高于所花星星的总和，于是用户会为了**保护**它而行动。
- **蔡格尼克效应**：饥饿条是未完成事件，会产生轻微的心理张力直到被关闭。饥饿状态会被文案放大（"看我这么可爱，忍心吗？"）。
- **损失厌恶**：宠物不会死（把惩罚写成死亡会毒化整个循环），但会 visibly 蔫下去。避免损失比争取等量收益更能驱动行为。

三条刻意设计：**成长只由照顾次数驱动**，与花了多少星星无关，所以连续买最贵的零食并不能加速进化——由"到场次数"决定，是为了保护这个功能的初衷；**星星不够时它反过来撒娇**（"再去赚点星星回来嘛"），把挫败感转成动机而不是弹报错；**宠物状态完全独立于星星账本**，它既不考核也不惩罚，是星星的去向而不是新的任务。

## 四、星星经济

### 收入项

| 行为 | 星星 | 备注 |
|---|---|---|
| 计划打卡 | +3 | 每日一次 |
| 完成计划 | +23 | 20 基础 + 3 打卡 |
| 完成待办 | +5 | 每条可自定义 0–9999 |
| 记录新学内容 | +2~+4 | 按难度：简单 2 / 中等 3 / 有难度 4 |
| 完成一次复习 | +1~+6 | 按难度 × 自评：想起来了 3/4/6、模糊 2/2/3、忘了 1；约 15% 概率翻倍 |
| 首次启动礼包 | +10 | 新手 endowment，见下 |

复习奖励刻意做成"忘了也给 1 星"：如实自评必须有收益，否则为了保护星星而一律点"想起来了"，整个排程就失去了输入信号。

### 支出项

抽奖按所中奖项定价。**宠物**：照顾动作 5–12 星，装扮 15–70 星。**余额不足时拒绝消费，绝不产生负数。**

### 定价校准

约 **3 次打卡（9 星）≈ 1 次抽奖（5–10 星）**。

这个比例是刻意设计的：奖励太难获得就不再是奖励。定价过低则抽奖失去分量感，定价过高则闭环断裂、用户攒不到放弃。

### 账本设计

`star_ledger` 表采用 **append-only** 模型：

- 每次变动记录 `delta`（增减量）、`balanceAfter`（变动后余额）、`reason`（变动原因）、`createdAt`
- 当前余额 = 所有 delta 求和，永远可从历史重算校验
- 撤销待办时写入负 delta 而非删除记录，**账目始终可审计**

## 五、心理学机制

每个机制在 `core/RewardEngine.kt` 中均标注了理论出处，确保后续修改不会破坏设计意图。

| 理论 | 提出者 | 实现方式 |
|---|---|---|
| **可变比率强化** | Skinner | 加权随机抽奖 + 减速揭晓动画，奖励频率不可预测 |
| **目标梯度效应** | Kivetz | 进度条用幂曲线缓动（1-(1-r)^2.2），末端视觉加速 |
| **禀赋效应** | Nunes & Drèze | 每日目标非零起始；首启赠送 10 星先体验完整循环 |
| **损失厌恶 / 连贯性** | Kahneman | 连续打卡天数显式追踪并展示，破坏连胜读作"损失" |
| **自我决定理论** | Deci & Ryan | 文案肯定能力与自主，零内疚设计 |
| **蔡格尼克效应** | Zeigarnik | 未完成计划常驻首页，保持适度注意力张力 |
| **快速早期胜利** | — | 幂律等级曲线，前期升级快 |

### 等级曲线

等级阈值采用**幂律增长**（`60 × level^1.613`，上限 100 级）：前期升级快以快速建立习惯，后期需要持续投入才有意义。

**技术说明**：阈值由闭式公式预计算成表，等级通过二分查找定位。闭式求逆（`pow` + `toInt`）在整数截断下无法自洽——每个等级边界回退一级，导致每次升级瞬间进度条跳到 100%。该问题在单元测试中被发现并修复。

**分层依赖方向**：UI → ViewModel → Repository → Room，单向依赖。Repository 是唯一修改星星余额的位置，保证奖励记账集中可审计。

### 数据表（10 张）

| 表 | 用途 | 索引要点 |
|---|---|---|
| `prizes` | 奖项池 | — |
| `draw_records` | 中奖记录 | `createdAt` |
| `plans` | 任务计划 | — |
| `plan_check_ins` | 打卡记录 | **唯一索引 `(planId, dayKey)`**、`dayKey` |
| `todos` | 待办 | `isDone`、`priority` |
| `foods` | 食物池 | — |
| `review_items` | 学习内容与其 SM-2 调度参数 | `nextDueDay`、`createdAt` |
| `review_log` | 复习历史（append-only） | `reviewedDay`、`reviewItemId` |
| `pet` | 宠物单条记录（id 固定为 1） | 主键即 id |
| `star_ledger` | 星星账本 | `createdAt` |

数据库版本 **v6**，每次升级都是写入式迁移（手写 SQL），老用户升级保留全部星星、计划、连续记录与复习进度。`fallbackToDestructiveMigration` 仅作为未知版本路径的最后兜底。

`review_items` 的到期时间存的是 `yyyy-MM-dd` 日期键而非时间戳：ISO 日期串的字典序等于时间序，因此"是否到期"在 SQL 里就是一个 `<=` 比较，查询时不需要任何时区换算。

全部 UI 状态经 Room `Flow` 驱动，DAO 变更自动刷新界面，无手动刷新逻辑。

### 测试

**54 项单元测试全部通过**（debug / release 变体各跑一遍）：

- `RewardEngineTest.kt`（16 项）：星星经济全链路
  - 加权随机：空池、零/负权重、权重分布偏差（4000 次抽样统计）
  - 目标梯度缓动：单调性、边界值、末端加速
  - 禀赋效应：非零起始、不回退、范围约束
  - **等级阈值与 `levelFor` 互逆性**（该测试曾抓出真实 bug）
- `SpacedRepetitionTest.kt`（11 项）：SM-2 自适应调度
  - 间隔序列 1 → 3 → 乘性增长；遗忘重置连续计数但保留易记因子
  - 易记因子上下界、最小随机也会严格增长（防止间隔卡死）
  - 出师由间隔长度定义；难度越高越晚出师（同样的完美自评）
  - 各难度下"想起 > 模糊 > 忘了"且失败仍有收益；奖励概率的实际抽样率校准
- `PetEngineTest.kt`（24 项）：宠物状态机
  - 衰减速率：约 20 小时耗尽饱腹、40 小时耗尽心情，且重复读取不二次扣时
  - 每天两次照顾不会跌到底（该测试直接推动了衰减常数的修正）
  - 负时间差不会"回血"；表情优先级：进食 > 久别 > 饥饿 > 心情
  - 每种表情的台词多于一句（避免录音感）；商店 id 唯一且价格在可及区间
  - 两次/天的照顾强度足以维持（功能可达成性验证）
  - **等级永不封顶**：越过最终形态后等级仍在增长
  - **等级边界自洽**：任意照顾次数都落在其级别对应的区间内，负数次数不越界
  - 每个部位都有买得起的起手物，也都有值得攒钱的稀有/传说款
  - **默认锚点必须连字形本身都不出框**（旧写法把帽子推出画布，是本 Bugs 的根因）
  - 位置微调按"每件"记忆并支持序列化往返；对齐一件不会带动另一件
  - 单件复位不影响其他件；疯狂甩拖被钳制；脏数据跳过而非崩溃
  - 便宜 day hello：最低价动作 ≤ 5⭐，且价格分布足够宽
  - 完整模拟跑到"出师"，校验终点落在第 60 天
  - 出师边界、超界轮次不崩溃、逾期天数为负、复查迟到不被惩罚
- `TimeUtilsTest.kt`（4 项）：日期键稳定性、日期间隔、负值时钟钳制
- `DailyCycleTest.kt`（8 项）：日边界归属
  - 昨天的打卡记录不影响今天；今天的记录被识别；同一天多条去重
  - 日键与零点时间戳互逆；`now` 必然落在"今天"区间内
  - 距下一个当地时间零点始终为正且不超过一天

### 测试抓出的真实缺陷

| 缺陷 | 表现 | 修复 |
|---|---|---|
| 等级公式自相矛盾 | 每次升级进度条瞬间跳到 100% | 闭式求逆改为阈值表 + 二分查找 |
| 禀赋基线被抵消 | `starsToday - BASE` 未赚星时为负归零 | 改为 `starsToday + BASE` |
| 打卡状态跨天不重置（v1.4.1） | 打过卡的计划第二天仍是灰色不可点；首页"今日星星"同样滞后 | 「今天」改为随时间推进的数据流，界面状态由其派生 |
| 宠物成长有天花板（v1.5.0） | 照顾 60 次后永远是"已经是最终形态"，此后再无反馈 | 形态与等级拆开；等级每 20 次照顾升一级且无上限 |
| 装扮位置偏出画布（v1.5.0） | 帽子/项链对不准，用户无从修正 | 锚点改为相对画布中心；新增拖动调整，位置按件记忆 |

这两个都是逻辑缺陷而非编译错误，靠手动点击界面很难发现。

## 九、设计决策记录

记录几个非显而易见的决策及其原因，便于后续维护时理解。

| 决策 | 原因 |
|---|---|
| 星星账本用 append-only 而非余额字段 | 余额可从历史重算，异常可被发现；直接改余额字段则无法追溯 |
| 打卡去重放在数据库唯一索引 | 应用层判断在并发下不可靠；唯一索引是最后防线 |
| 抽奖星星从"抽中的奖项"扣除 | 先选定再扣费，保证扣费金额与实际所得奖励一致 |
| 短休息奖励压到 2 星 | 防止奖励结构反向激励"刷休息"而非工作 |
| 首页先显示等级而非任务 | 先定向再行动，避免任务列表带来的压迫感 |
| 进度条末端加速 | 目标梯度效应：最后阶段是放弃率最高点，需强化冲刺感 |
| 撤销待办退还星星 | 保证账本忠实反映"已获得"，而非"当前持有" |
| 「今天」由数据流下发而非读一次缓存 | 零点没有数据库写入，缓存的日期会跨天存活，打卡状态便永不复位 |
